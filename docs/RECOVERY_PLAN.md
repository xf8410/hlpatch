# SO 文本异常、闪退与续养恢复：诊断及修复方案

日期：2026-10-03。范围：`hlpatch` v3.28.2 / v3.28.4 发布链、本地 `so-history-backup` 镜像、旧 Android 客户端及 PR #27 合入后的客户端、公共运行层。

本轮完成源码核对、发布链重放和宿主隔离探针。没有设备，没有执行游戏 Hook，没有修改生产代码，也没有部署、提交或推送修复。文中的修复批次是实施方案，不是已完成的修复。

## 1. 结论与优先级

应先修 SO 对游戏的干扰和大响应风险，再修采集与续养恢复，最后验收完整决策。不能把这几类现象归为同一个“轮询错误”。

1. **游戏文字被吞：有明确的代码触发条件。** 两个版本的 `TextCommon.set_text` 观察 Hook 在拿不到 trampoline 时直接返回，不调用游戏原 setter。隔离探针已证明该分支会吞掉文字更新；但尚未取得现场 trampoline 状态，不能断言它就是图片问题的唯一根因。
2. **大 JSON 内存放大：已用真实序列化代码复现。** 2 MiB 合成正文在 metadata 序列化期间达到约 26 MiB 的宿主峰值存活分配。手机是否因此 OOM、被系统杀死或触发其他原生错误，仍需崩溃证据。
3. **v3.28.4 闪退：尚未确诊具体函数。** 核心文本、嗅探和大响应风险在两个版本中共同存在，不能把共同缺陷直接说成 v3.28.4 独有回归。
4. **重启游戏后续养停止计算：必须按 APK/协议分代处理。** 旧 App 存在搜索键不足和线程状态卡住路径；交接版另有 SO 重启序号归零与持久局包身份碰撞问题。后者已做条件复现，但尚未证明存在于作者安装组合中。
5. **“收到数据”与“允许决策”必须分开。** 当前旧摘要适配无法生成完整 V1 状态；新 App 明确拒绝计算属于已知完整性边界。不能通过填零、伪造历史或绕过校验来恢复表面上的推荐。

## 2. 作者已确认的现场事实

- “再次上线”指**重新启动游戏，再进入未结束的育成**；是否同时重启 AI App 尚未确认。
- 相对稳定版本是 [hlpatch v3.28.2](https://github.com/xf8410/hlpatch/releases/tag/v3.28.2)。它并非无缺陷：开启嗅探会出现白条/红条，大 JSON 输出也曾导致闪退。
- 明确报告闪退的版本是 [hlpatch v3.28.4](https://github.com/xf8410/hlpatch/releases/tag/v3.28.4)。其准确触发步骤、崩溃信号和首个故障点仍未知。
- 白条/红条发生在**游戏自身的文字区域**。截图中图像和部分静态文字仍存在，动态文字为空，数值区显示 `123,456,789`、`99:99` 一类占位内容。这支持优先调查文本更新链；不能由截图推出服务器上的角色、货币或账号数据被修改。
- 作者的操作涉及 `/api/md5log/install`、`/api/md5log/clear`、`/api/sniff/toggle?enabled=1`，不是只有读取 `/api/sniff/diag`。安装和开关调用必须纳入复现步骤。
- 触发大 JSON 的具体端点、现场 APK 版本、Hachimi 宿主版本、游戏版本尚未确认。

## 3. 版本与源码对应关系

### 3.1 本地镜像不等于最终发布源码

本地 SO 仓库是 `so-history-backup@721c086220ea081523229d88623de5abddd97eaa`。远端镜像没有 v3.28.2 / v3.28.4 发布标签，真正发布来自 `xf8410/hlpatch`。发布流程会在基线之上运行累计生成器和补丁，因此仅检查镜像中的 `hachimi_ura_plugin/src/lib.rs` 不足以判断安装包行为。

本轮已在独立临时目录重放两个发布流程，比较最终生成的 `lib.rs`。关键事实：

- v3.28.2 的 tag 指向 `a86707e`，发布 manifest 的构建源码提交为 `fa2c820`；二者不能互换。
- v3.28.4 发布源码提交为 `5a2ac3e`。相对 v3.28.2 谱系，包含 meta 查询、版本输出改造、停用内置 AI、移除屏幕镜像安装等差异。

## 4. 具体发现及证据边界

以下 `G2`、`G4` 分别表示本轮重放的 v3.28.2、v3.28.4 `generated-lib.rs`。`W` 表示当前本地 SO 工作树，包含尚未进入上述发布包的 V1 交接改动。每项均注明适用范围。

### F1 — 全局文本 Hook 缺少原调用保障（最高修复优先级）

证据：G2:24731、G4:24923 的 `text_common_set_text_hook_handler` 函数逐字相同；生成器为 `scripts/apply_hachimi_textcommon_observer.py`。

- `trampoline == 0` 时直接 `return`，游戏原来的 `set_text` 不执行。
- 安装器只检查 Hook 安装返回非空，没有验证后续查询到的 trampoline 可用。
- `install_api_sniff_hooks` 入口安装 TextCommon 观察器。TextCommon 的观测代码没有使用 `SNIFF_ENABLED` 门控；单纯关闭协议记录不等于恢复未安装文本 Hook 的状态。
- `/api/sniff/toggle` 在解析 `enabled` 前就尝试安装 Hook。因此调用 `enabled=0` 也不能作为“从未安装任何 Hook”的干净对照。

隔离探针直接复用生成后的 setter 函数体，替换宿主依赖为计数器：

- trampoline 可用：原 setter 调用 1 次，通过。
- trampoline 缺失：原 setter 调用 0 次，期望“始终透传”的检查失败。
- 原调用成功后观察逻辑产生普通 Rust panic：原 setter 仍调用 1 次，通过。

因此，“所有观察 panic 都会吞文字”不成立；“缺失 trampoline 会吞文字”已由代码和探针确认。两版安装键与查询键一致，SIGSEGV 补丁只包装读助手，没有把该 handler 改名；本轮排除了所检查发布链中的 handler 名字错位假设。

尚需设备区分：trampoline 实际是否为零、是否与宿主汉化 Hook 冲突、完整原生签名是否匹配、重复安装或并发安装是否改变调用链。普通 Rust `catch_unwind` 不能作为任意原生非法访问已被安全处理的证明。

另一个可确定的安装差异：G2:11763 将 MakeMd5 和 ComputeHash 的安装都放在 `MAKEMD5_ADDR == 0` 分支内。作者先单独调用 `/api/md5log/install`，再开启嗅探，会使后续安装路径跳过 ComputeHash。因此“只开嗅探”与“先装 MD5 再开嗅探”不是同一个测试条件。两版静态 `SNIFF_ENABLED` 都初始为 true，作者所见“默认关闭”需以现场状态端点和实际 Hook 集合核对，不能直接覆盖源码事实。

### F2 — 大 JSON 生成、缓存和传输缺少字节预算（最高修复优先级）

下列公共路径在 G2/G4 中相同：

- `push_sniff_metadata`，G2:381：完整正文转为约两倍大小的 hex；缓存只限制 1000 条，没有总字节预算。
- `/api/sniff/metadata`，G2:8154：把 `after_id` 后的所有记录一次返回。持 `SNIFF_MUTEX` 构建每条字符串、字符串集合、join 结果及最终 JSON，没有分页和总响应字节限制。
- `handle_http`，G2:9942/9948：普通响应和 `?dl=1` 均把整个 body 再拼进 HTTP 字符串。`dl=1` 不代表流式下载。
- `storage_download`，G2:24421：整文件读取、计算校验值、转完整 hex、拼 JSON，再进入通用 HTTP 包装。
- `storage_turn_event_jsons`，G2:25268：有记录数限制，但读取、MessagePack 解码和部分 JSON 构造发生在游标过滤之前，且没有输出字节上限。
- 通用响应还经过 `save_endpoint_log` 全文落盘；这是额外 IO，不应一概描述为额外整份堆复制。

宿主探针输入 8 × 256 KiB 合成正文，复用真实 metadata helper 与序列化分支：

- 原文总量：2,097,152 字节。
- metadata 响应：4,195,447 字节。
- 常驻分配器请求量：6,292,672 字节。
- 序列化峰值存活分配：27,269,649 字节。
- HTTP 包装阶段峰值存活分配：18,879,104 字节。

这是 Windows 宿主分配器请求字节统计，不是 Android RSS/PSS、OOM 阈值或手机延迟。它足以证明放大路径，不能证明现场退出原因。需区分 SIGSEGV、SIGABRT/分配失败、LMKD 杀进程与 ANR。

### F3 — 网络观察与大响应争用同一把锁（高优先级）

G2:10785 的响应 Hook 和 :10859 的 POST Hook 持有 `SNIFF_MUTEX`，锁内调用 `persist_protocol_capture`。该函数在 :23775 执行文件写入、同步、重命名、SQLite 事务及语义扫描。metadata HTTP 序列化也持同一把锁，可能阻塞游戏请求/响应线程。

网络 `write_all` 发生在 metadata 分支锁释放后，不能误报为“持该锁发送整个 HTTP”。但 HTTP 入口每连接新建线程，缺少并发连接总量控制，仍可能叠加多个大响应的资源占用。

这证明共享锁与 IO 耦合，不证明图片中的全部 UI 异常都是争锁造成。需要测量 Hook 时长、等待时长、游戏帧时间与发生异常的顺序。

### F4 — 续养的传输恢复与状态就绪被混在一起（高优先级）

W 的 fresh summary 每次重新调用宿主 API，读取 `WorkDataManager → SingleMode → Character`（`lib.rs:4667`）。不能直接把问题归为“进程重启后还使用上一次角色指针”。

但存在以下明确控制流：

- 启动探测最多先跑 60 轮，每轮 1 秒；随后读取错误可退避 5–60 秒，再叠加常规轮询间隔（W:6697、6740）。较晚进入续养时可能延迟发现育成状态。
- `GAME_INITIALIZED=false` 时，HTTP 对摘要/快照入口返回 200 booting（W:7458），App 更频繁地请求也不一定促成重新采样。
- 推送前就更新 `LAST_PUSH_HASH`，连接失败后同内容可能不再推送；没有可靠成功 ACK 与完整读超时控制（W:6672、6781）。
- 交接版 App 的任意已交给回调的推送都先更新 `lastPushAt`，5 秒内暂停 pull。旧摘要、不完整快照也可延后 V1 轮询（`FloatingWindowService.java:103,208`）。

应分别观察“端口可达、游戏进入育成、采集完成、协议校验通过、任务入队”，不能用一个“已连接”状态涵盖全部阶段。以上路径需与发布生成源码及作者实际 APK 对上，才可归因现场。

### F5 — 当前 V1 实现未解决同一育成跨采集进程的身份与序号恢复

适用范围是交接 V1，不能当作已发布 v3.28.2/v3.28.4 的已知现场根因。

- SO `Publisher` 只有进程内 `serial`；重启从 1 计数（`ramen_observation/src/lib.rs:32`）。
- Android `SnapshotOrderTracker.java:13`、`LatestRequestQueue.java:20` 拒绝同一 run 的低序号。真实类探针验证 seq40 → seq1 被拒绝。
- 即使 AI App 也重启，`RunArchive.java:35–38` 仍按 run/seq 读到旧文件；新内容复用旧 seq 会抛身份碰撞错误。服务先存档后检查水位，这一错误可能先出现。
- 公共 `RamenSession` 同样要求同一 run 的 seq 递增，只改 Android 去重不能修完整链路。
- 当前 `read_ai_snapshot` 在 `read_summary` 已发布后再次发布。真实 Publisher 探针构造出“新体力 80 已发布，迟到缓存 70 又取得更高 seq”的时序模型。需要统一唯一发布者，而不是给旧内容重新盖上新时间。

当前 legacy→V1 转换还固定缺 run/stage/continuation，通常先被完整性检查拒绝。补齐真实 V1 后，若同一 run 的采集进程重启导致低序号或序号复用，上述水位拒绝或档案碰撞仍可触发。

### F6 — 旧 APK 有两条独立的“不再计算”路径

仅针对 `ccbf978` 的旧 `FloatingWindowService.java`：

- :526 的 `searchKey` 不含阶段、人员分布和完整训练候选。抽取原方法后，“吃面选择→训练＋人员变化”得到相同 key，无法触发重算。
- :550–556 先设 `searchRunning=true`，然后若旧线程仍存活就返回。受控线程探针复现 `searchRunning=true`、`workerAlive=false`，会持续显示搜索中。

这两处旧版方法与 Git 基线逐字校验一致，对应两项条件探针均得到预期失败。另三项水位、队列及持久局包探针针对交接版，见 F5。探针没有启动 Android Service、JNI 或真实搜索，不能替代设备复现。新主线已经使用不同调度结构，不能把旧问题重复报成新主线同一缺陷。

### F7 — 回合语义尚未建立可追溯的转换依据

W:4740 的注释要求 raw 含义待确认，随后却把拉面 `_totalTurnNum` 直接当累计回合并按 24/48 分年；输出又声明语义 verified。而 `/debug/turn_probe` 仍称 countdown/unverified。这是明确的契约矛盾，不足以证明正确答案就是加一、减一或反转倒计时。

现有两份校验通过的请求样本仅显示 `current_turn=3`，没有同一时刻的内存 raw、UI 与阶段配对；另一份 exec_command 样本校验值不符，不能当作权威标定依据。修复前需要采集同一观测边界的原始值与实际回合，并覆盖开局、年份交界、事件、比赛和最终结算。

### F8 — 全局信号恢复缺少故障线程归属（最高修复优先级）

G2:842 使用全局 jump buffer 和恢复布尔值；:912–921 的 handler 仅检查该布尔值便 `siglongjmp`，没有核对当前故障线程是否为建立恢复点的线程。若其他线程恰在该窗口收到信号，存在跳向另一线程执行上下文的危险。两版函数相同，不能直接用它解释 v3.28.4 独有回归；本轮未执行非法访问或跨线程跳转实验。

此外，G2:898 在判断是否可恢复之前就写入 `RECOVERED`。随后仍可能重新触发信号终止进程；该字样不能作为“成功恢复”的证据。修复必须先保障故障证据可信，再讨论是否能够安全恢复，不应让全局恢复器处理所有线程的任意错误。

## 5. 修复方案：按依赖拆成可回退批次

### 批次 A：冻结可复现的 SO 基线并补足诊断

从 v3.28.2 的实际发布生成链建立独立修复分支，保护现有镜像和 V1 未提交改动。固定基线、每个生成脚本的提交与 SHA256，禁止发布时再读可变 main；保存最终生成源码、SO、未剥离符号、Build ID 和完整构建清单。v3.28.4 作为对照，不把它未经验证的变化一次性全部搬入。

诊断最少增加：插件版本/源码指纹、游戏和宿主版本、Hook target/handler/trampoline、安装次数、安装线程、原调用次数、观察次数/失败数、每类耗时；状态输出保持小且有界。明确区分配置的 capture 开关与实际已安装 Hook 集合，不能凭界面显示“关闭”判定不存在 Hook。

**验收：** 干净检出能重建同一源码组合；作者核对安装 SO 的 SHA；关闭、安装、开启三个状态可分别识别；每次故障能关联到端点/Hook 和版本。

### 批次 B：先保证游戏原调用，再恢复必要观察

第一份诊断候选在冷启动时不安装本插件的 TextCommon Hook，保留游戏原文字和宿主汉化链，用同一菜单、育成和同一操作序列与 v3.28.2 对照。仅关闭记录开关或跳过日志写入不够，因为仍可能保留吞掉 setter 的分支。不要同时改搜索、回合转换和内存管线，以免无法归因。

后续修复要求：

- 安装提交前取得并校验原调用入口；拿不到 trampoline 时拒绝或回滚该 Hook，不能留下“已替换但无法转发”的 handler。
- 一个目标由单一安装入口和状态机管理，防止重试/并发/宿主 Hook 冲突。验证完整方法签名，而不只看名称和参数个数。
- 原调用与观察分离，原方法按正确参数恰好执行一次；只隔离观察部分的失败，不返回人为的 null/零值冒充原结果。
- 文本观察可独立开关。协议嗅探不隐式启用全游戏文本记录；TextCommon 不作为训练当前状态的唯一来源。
- MD5 独立安装、协议收发、Unity 回调和文本观察逐组测试。诊断时每组冷启动，不用 `toggle=0` 假装撤销已安装 Hook。
- 修正 F8：停止跨线程共享跳转恢复；记录实际故障线程、信号及恢复结果。不能只加线程 ID 判断就宣称安全，仍需检查跳转是否跨越 Rust 活跃对象、锁及析构边界。首轮候选优先使用不改变原故障语义的最小日志，并保留系统/宿主的原生崩溃处理链。

**验收：** 宿主 spy 覆盖正常、无原入口、观察 panic、重复安装和并发安装；核实原参数、ABI 要求的隐藏参数及返回值保持，兼容宿主已有的同目标 Hook 链；拿不到原入口时目标保持未替换或确认回滚成功。调用次数探针不能独自证明 ABI 正确。信号处理审查确认没有跨线程跳转或虚假恢复日志；设备上相同文字输入/原结果不受观察开关影响，无占位数字、空白文字和误写游戏状态。没有该证据前，不恢复默认文本观察。

### 批次 C：使大响应与记录量脱钩

优先复用已有 `storage_read_range` 的固定 64 KiB 缓冲及直接流式返回路径（G2:25035），不要另造一个全量 JSON 下载接口。

- metadata 只返回索引、明确标注的短预览、原始文件引用、字节数及校验值；同时限制条数和 UTF-8 响应字节数。
- 原始正文完整保存于 raw 文件；大文件通过 range/流式下载并校验长度和 SHA256，禁止先整文件转 hex。
- 先用游标/索引过滤，再读取和解码目标记录；对单条过大的解析结果返回明确状态及 raw 引用。
- 锁内只做队列/快照交换，锁外完成序列化、文件 IO 和数据库操作。给捕获队列设置字节预算，给导出设置并发上限。
- 数据拥塞或磁盘失败必须明确记录缺口/暂停捕获状态，不能无限扩容、长时间堵住游戏线程或静默丢弃后声称完整。
- 健康/状态接口与大导出隔离。大 body 不重复写入通用端点日志，改记请求标识、实际字节数、耗时和错误。

建议首轮测试配置为 metadata 每页最多 64 条且不超过 256 KiB、原始块不超过 1 MiB、同时导出不超过 2 个；这是待设备验证的工程起点，不是已验证的安全阈值。单条超限走 raw 文件，不能裁掉原文后继续标为完整。

**验收：** 用 1/16/64 MiB 合成 raw 和多连接做宿主压力测试，确认分页/流式缓冲上限、内容 hash 一致及断开后的资源释放。作者手机同时运行游戏验证 PSS、帧时间、Hook 阻塞、健康接口响应及崩溃/LMKD 记录；不能只测浏览器下载成功。

### 批次 D：恢复采集与可靠传输

采样仅在已验证安全的游戏状态/线程边界生成不可变观测。后台推送和 HTTP 读取同一缓存，HTTP 不再触发另一套游戏对象扫描或再次发布旧缓存。明确 `booting → waiting_for_run → capturing → ready / incomplete / error`，分别记录最后采集、最后发送、最后确认时间。

每次续养重新取得真实局标识和当前完整状态；初始化回调丢失时有独立、有限的主动状态探测，不能被 60 秒错误退避长期掩盖。回合字段保留 raw 值、来源与已验证转换；在完整样本核对前不写 verified。

推送采用有限超时、确认与重试：发送失败不更新“已确认”水位；同一快照允许重传。ACK 区分“收到/已校验/拒绝原因”，不把成功接收宣称为完成计算。App 只有接收同一采集世代的有效新快照后才能短暂抑制 pull，并保留最大健康探测间隔；旧协议、错误或不完整推送不能无限遮蔽新快照端点。

**验收：** 覆盖 App 后启动、第一次推送失败、游戏先启动但晚进入育成、断连重连、同快照重发、迟到旧缓存。每一步可区分通信成功与状态完整。

### 批次 E：明确跨进程续养契约，再接完整决策

推荐新增独立 V2 envelope，增加 `collector_instance_id`。育成身份 `run_id` 在续养时保持稳定；SO 每次启动产生新 instance；`snapshot_id` 只在该 run/instance 内递增。统一身份为 `(run_id, collector_instance_id, snapshot_id)`。

- Android 接收、水位、队列、请求提交校验、JNI、Rust 会话和局包同时支持新键；旧世代迟到结果继续拒绝。
- 用握手/能力端点确认当前 instance，新世代第一份完整快照触发重建实时会话。不能见到任意小序号就自动清空水位。新会话的运气基线不能冒充整局基线；无法验证连续性时标明恢复点和历史缺口。
- 局包中的 envelope、标准状态快照、决策及结果均携带或映射 instance 身份；文件命名、CSV 关联键、打包器和复盘读取器同步迁移。不能只改变 envelope 目录而留下标准快照重名或旧读取器漏读子目录的问题。旧局包保留为 legacy 世代，不覆盖同名文件。
- 保留 V1 原有语义，通过能力协商选择 V2；不让旧 APK 静默误读改变后的序号规则。推送按 schema 分流，轮询选择支持的版本端点。
- 单纯持久化 seq 只有在原子落盘、无并发生产者、备份恢复不回退等条件全部成立时才可靠，不作为唯一的进程身份。

恢复实时决策需要**当前完整 state + continuation**，不是必须从开局重放所有网络包。实际 RMJ 结果、当年吃面次数等必要状态应从游戏持久状态或有来源证据的局记录取得；拿不到就列出具体缺项。在当前必要状态已完整且校验通过的前提下，缺失早期历史主要影响累计运气和完整复盘，应分别标记。

若作者仍使用旧 APK，可对 F6 做有限热修复；主线继续使用公共会话与新调度器，不恢复旧固定卡组、GA 或模拟历史作为生产兜底。

**验收：** 同一育成游戏进程重启 3 次、AI 保活/同时重启两种情况都能恢复；档案无覆盖，旧 instance 消息不能倒灌。随后按同快照、同配置、同种子、同并行度对照 PC/ARM64，比较阶段、合法候选与最终动作。

## 6. 作者最小验证任务

先做小范围定位，再做整局/长时验收。开发方没有设备，以下由作者执行；现阶段不需要上传全部账户报文。

1. **版本身份：** 记录 SO 文件名/SHA、APK 包名/versionCode、游戏与 Hachimi 版本，保存正在使用的配置及回退产物。区分游戏进程、AI 主进程、`:engine` 和浏览器/抓取客户端。
2. **文本问题：** 固定 v3.28.2，同一场景下记录冷启动、MD5 安装后、协议嗅探开启后、关闭记录后各自的 Hook 状态与首次文字异常时间。用诊断候选验证“仅不安装本插件 TextCommon 观察器”是否消除异常。
3. **大 JSON：** 先报告具体 URL、是否带 `dl`、after 游标、数据积累时长/条数、客户端类型、响应大小及哪个进程退出。已知会崩的无界端点不作为常规轮询源；压力验证在修复候选和保留日志的条件下进行。
4. **v3.28.4：** 记录冷启动是否已崩、进入育成才崩，还是首次调用特定端点后崩。拿相同配置和操作与 v3.28.2 对照；没有实际调用新 meta 端点时，不能仅凭版本新增该功能就归因 SQL/资源库。
5. **续养：** 固定同一局，采集游戏退出前、重启后但尚未进入育成、进入育成后这三个边界的 `/summary`、支持的快照端点及 `18766/status`。记录局 ID、instance、seq、raw turn、显示回合、阶段、ready/missing_fields 和时间，不用图片替代字段证据。

故障日志至少保留 `ura_boot.log`、`uma_predict.log`、Android crash buffer；如系统允许取得 tombstone，也保存原件。符号化必须使用同一 Build ID 的未剥离 SO。可参考 [Android ndk-stack](https://developer.android.com/ndk/guides/ndk-stack) 和 [原生崩溃诊断](https://source.android.com/docs/core/tests/debug/native-crash)：

```text
adb logcat -b crash -v threadtime -d > crash.txt
ndk-stack -sym <匹配构建的未剥离符号目录> -dump crash.txt
```

日志先本地留存，再提供去除账号令牌、Cookie、认证请求和无关个人数据的诊断副本。原始证据保持不变，派生脱敏副本单独保存。无需为了取证清除育成数据、卸载旧 App 或修改在线游戏数值。

最终仍需完成原计划的完整阶段、至少 10 局及连续 2 小时稳定性与性能验收；这些不能由本轮宿主探针或 CI 构建代替。
