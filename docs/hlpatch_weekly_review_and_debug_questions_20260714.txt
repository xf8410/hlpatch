- action变成Unknown或误判；
- turns缺失；
- training_sessions无法正常上传。

九、DataCollector自身的确定性Bug
============================================================

即使 /summary 修复，当前 DataCollector 仍有以下代码问题，请逐项确认并提出commit级修复方案。

1. 异步上传读取变化后的sessionId

uploadCurrentSession()先构建旧session的JSON，然后uploadToGitHub()新建线程。线程内又读取成员：
- sessionId
- scenario
- turns.size()

主线程可能已经startNewSession，导致JSON属于旧局，但文件名和目录属于新局。

仓库已有直接证据：
- training_sessions/Ramen/de09c02b.json 内部 session_id 是 12c4b72b；
- training_sessions/Ramen/f41b5f65.json 内部 session_id 是 1b4ffed4。

请解释文件名和内部session_id为何不一致。

2. 重复startNewSession

回合重置时：
finalizeAndUpload();
startNewSession();

final上传成功后异步线程又：
if (isFinal) startNewSession();

这可能清空已经开始采集的新局。请说明是否确认发生过，准备如何删除网络线程对采集状态机的修改。

3. 假恢复

restoreSession只恢复：
- sessionId
- savedTurnCount

但不恢复：
- turns
- prevSnapshot
- scenario

所以App重启后看似恢复，实际历史数据已经丢失。已有文件从turn 22才开始，符合中途重启/Collector重建后的残片。

4. GitHub并发覆盖

每回合启动一个线程，多个线程可能GET到同一个旧SHA；第一个PUT成功后，第二个用旧SHA会收到409。

请提供是否出现过401、403、409和超时日志，并说明如何改为单线程上传队列。

5. 正确修复建议

上传前应冻结不可变快照：
- uploadSessionId
- uploadScenario
- uploadTurnCount
- uploadJson
- path

网络线程只能使用快照，不得再读取或修改当前Collector状态。

建议使用单线程Executor，网络成功/失败不调用startNewSession。当前session切换只允许由采集状态机执行一次。

6. 本地持久化

是否应每回合先写本地JSON，再异步同步到GitHub？App重启后从本地完整恢复，GitHub只作为副本，不能作为实时状态机的一部分。
